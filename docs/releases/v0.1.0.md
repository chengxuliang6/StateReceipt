# StateReceipt v0.1.0

[简体中文](v0.1.0.zh-CN.md) | [Español](v0.1.0.es.md)

StateReceipt v0.1.0 is the first public milestone of the StateReceipt specification draft and Python reference implementation.

StateReceipt records point-in-time claims about AI-assisted work together with explicit evidence, artifact snapshots, validity dependencies, and deterministic freshness/staleness checks. Its core question is deliberately narrow: **which previously recorded work-state claims are still supported by the artifacts that exist now?**

## Highlights

- StateReceipt v0.1 JSON Schema and normative specification.
- Explicit Claim–Evidence binding with SHA-256/SHA-512 artifact snapshots.
- Deterministic Claim evaluation, including dependency-aware `stale` behavior.
- Cross-platform CLI: `init`, `capture`, `validate`, `validate-chain`, `verify`, `inspect`, and `diff`.
- Immutable Receipt lifecycle links through optional predecessor IDs, with local cycle/self-reference validation.
- Safe-by-default verification: Receipt commands are never replayed unless both `--replay --trust-receipt` are supplied.
- Five-minute end-to-end Quick Start plus first-party English, Simplified Chinese, and Spanish documentation.
- Python, FPGA/Verilog, and MATLAB example Receipts.
- Optional in-toto Statement / DSSE interoperability guidance without custom StateReceipt cryptography.
- CI across Ubuntu, Windows, and macOS on Python 3.11–3.13.
- Wheel and sdist build + clean-install smoke tests, including packaged schema verification.

## Important semantics

`stale` does **not** mean a Claim is false. It means the evidence captured for the earlier snapshot can no longer be relied upon for the current state and the Claim requires re-evaluation.

A structurally valid Receipt is also not proof of producer identity. v0.1.0 does not define signatures or producer authentication.

## Replay safety

Normal verification does not execute commands:

```bash
statereceipt verify receipt.yaml
```

`--replay` alone is refused. Execution requires an explicit acknowledgement:

```bash
statereceipt verify receipt.yaml --replay --trust-receipt
```

StateReceipt is **not a sandbox**. `--trust-receipt` means that the caller has inspected the Receipt and accepts the execution risk; it is not an authentication or safety guarantee.

## Lifecycle

Receipts are immutable point-in-time artifacts. A later Receipt can name one direct predecessor. The local chain validator can detect duplicate IDs, self-reference, and cycles while allowing unresolved/external predecessor IDs.

```bash
statereceipt validate-chain sr-a.yaml sr-b.yaml sr-c.yaml
```

## Interoperability

The exploratory interoperability profile maps the complete StateReceipt document into an in-toto Statement predicate and projects artifact digests into subjects. If authenticity is required, DSSE can be layered around the Statement by an external implementation.

Unsigned local Receipts remain fully conforming. A valid signature would authenticate bytes under the selected external trust policy; it would not prove that a natural-language Claim is true or that the recorded work is correct.

## Explicit non-goals

StateReceipt v0.1.0 is not:

- a persistent AI memory database;
- a RAG/vector system;
- a chat-history synchronization format;
- an agent orchestrator or scheduler;
- a process/network/filesystem sandbox;
- a cryptographic signing system or PKI;
- an automatic truth judge for AI-generated Claims.
