# StateReceipt v0.1.0 (Español)

[English](v0.1.0.md) | [简体中文](v0.1.0.zh-CN.md)

StateReceipt v0.1.0 es el primer hito público del borrador de la especificación StateReceipt y de su implementación de referencia en Python.

StateReceipt registra afirmaciones sobre el estado de trabajo asistido por IA en un instante concreto, junto con Evidence explícita, instantáneas de artefactos, dependencias de validez y comprobaciones deterministas de freshness/staleness. La pregunta central es deliberadamente concreta: **¿qué afirmaciones registradas anteriormente siguen respaldadas por los artefactos que existen ahora?**

## Aspectos destacados

- JSON Schema StateReceipt v0.1 y especificación normativa en inglés.
- Vinculación explícita Claim–Evidence e instantáneas SHA-256 / SHA-512 de artefactos.
- Evaluación determinista de Claims, incluido comportamiento `stale` sensible a dependencias.
- CLI multiplataforma: `init`, `capture`, `validate`, `validate-chain`, `verify`, `inspect` y `diff`.
- Ciclo de vida de Receipts inmutables mediante predecessor IDs, con validación local de autorreferencias, ciclos e IDs duplicados.
- Verificación segura por defecto: los comandos de un Receipt solo se ejecutan con `--replay --trust-receipt`.
- Quick Start de cinco minutos y documentación de primera parte en English / 简体中文 / Español.
- Receipts de ejemplo para Python, FPGA/Verilog y MATLAB.
- Guía opcional de interoperabilidad in-toto Statement / DSSE sin criptografía propia de StateReceipt.
- CI en Ubuntu, Windows y macOS con Python 3.11–3.13.
- Construcción e instalación limpia de wheel y sdist, incluida la verificación de la Schema empaquetada.

## Semántica importante

`stale` **no significa** que una Claim sea falsa. Significa que la Evidence capturada para una instantánea anterior ya no puede utilizarse de forma fiable para respaldar el estado actual y la Claim debe reevaluarse.

Un Receipt estructuralmente válido tampoco demuestra la identidad del productor. v0.1.0 no define firmas ni autenticación del productor.

## Seguridad de replay

La verificación normal no ejecuta comandos:

```bash
statereceipt verify receipt.yaml
```

`--replay` por sí solo es rechazado. Para ejecutar se requiere una aceptación explícita:

```bash
statereceipt verify receipt.yaml --replay --trust-receipt
```

StateReceipt **no es un sandbox**. `--trust-receipt` solo significa que la persona que ejecuta ha inspeccionado el Receipt y acepta el riesgo; no es autenticación ni garantía de seguridad.

## Ciclo de vida

Los Receipts son artefactos inmutables asociados a un instante. Un Receipt posterior puede declarar un predecessor directo. El validador local detecta IDs duplicados, autorreferencias y ciclos, pero permite predecessors externos/no resueltos.

```bash
statereceipt validate-chain sr-a.yaml sr-b.yaml sr-c.yaml
```

## Interoperabilidad

El perfil exploratorio coloca el documento StateReceipt completo en el predicate de un in-toto Statement y proyecta los digests de los artefactos en subjects. Si se necesita autenticidad, una implementación externa puede envolver el Statement con DSSE.

Los Receipts locales sin firma siguen siendo plenamente conformes. Incluso una firma válida solo autenticaría bytes según una política de confianza externa; no demostraría que una Claim en lenguaje natural sea verdadera ni que el trabajo sea correcto.

## No objetivos explícitos

StateReceipt v0.1.0 no es:

- una base de datos de memoria persistente de IA;
- un sistema RAG/vectorial;
- un formato de sincronización de historiales de chat;
- un orquestador o planificador de agentes;
- un sandbox de procesos, red o sistema de archivos;
- un sistema criptográfico de firmas o PKI;
- un juez automático de verdad para Claims generadas por IA.
